# DECISIONS (what / why / alternatives)
- D001 Project root is /home/deeraj/AIFS_PROJ/palace (design doc copied in). Python 3.11 venv (.venv); system default 3.13 unsuitable for pinned stack.
- D002 Env: 17 GB free disk (>15 GB threshold but low), 15 GB RAM with ~13 GB used, ~3 GB free GPU. Strict disk strategy enabled (stream, never extract whole archives); GPU budget capped at ~2.5 GB.
- D003 Resident counts (source: Zenodo 15708568 description table, read 2026-10-14; exact text: "aruba 1 community-dwelling older adult milan 2 ... cairo, paris >2 ... tulum 2"). => Only Aruba is single-resident. Individual regime = Aruba only (n=1 home; any "individual" claim rests on one home). Milan, Tulum (2) and Cairo (>2) are treated as aggregate. All four still usable as home clients in FL.
- D004 Office zip is parsed streaming straight from the zip (no extraction) because RAM (~0 GB available) and disk (<17 GB) are tight; avoids the unexplained 108 GB expansion.
- D005 ASHRAE DB II data are directly on GitHub (v2.1.0/db_measurements_v2.1.0.csv.gz, ~3 MB, metadata csv) -> no Dryad manual step expected. BDG2 stored via Git LFS: fetch via media.githubusercontent.com.
- D006 Homes are short recordings (57–220 days), so min usable days for homes is 50 (offices stay 180). Under 70/15/15 with 7-day gaps, cairo and milan end up with 0 test days; they are excluded from test-split evaluation (kept only as FL training clients / noted in limitations). Alternatives: shrink the gap (would weaken leakage control), or leave-one-site-out only.
- D007 All home recordings are 2009–2011 (before the 2016–2025 weather window): home presence is replayed by (day-of-week, season) onto a fixed recent weather year; weather and occupancy therefore come from different years (to be listed in limitations).
- D008 Outage mask: a gap with no event of any kind > 24 h is MASKED (missing). Homes' presence is high (0.65–0.8) since residents are mostly home; the forecasting task is low-contrast there.
- D009 Python: reuse miniconda Python 3.13.5 with preinstalled torch 2.9.0+cu128 (CUDA works) via venv --system-site-packages; deviates from the 3.10–3.11 spec, because the cu124 torch download failed repeatedly on this link and the reused torch avoids ~2.5 GB of disk. Risk: some pinned libs (opacus/SB3) may lag 3.13/torch 2.9 — tested in Phase 4.
- BDG2 licence read from repo LICENSE: CC BY-SA 4.0. Office EUI (electricity only, 261 bldgs, >=80% hours present): p10=53, p50=124, p90=293 kWh/m2/yr. Mostly non-Indian climates: caveat.
- D010 Office zip md5 verified OK. Uncompressed total = 2.02 GB (NOT 108 GB; the Zenodo page figure is unexplained/wrong for this file). Files are comma-separated (date,time,sensor,msg), tokyo is .txt (910 MB). No disk strategy needed beyond streaming. ac2.csv is 4.5 KB => dropped (<180 days). Site list is decided from site_summary.csv, not assumed.
- D011 Event classification by message (ON=motion, OPEN/CLOSE=door) because sensor ids are semantic names at most office sites. LIMITATION: ac1, ac3, ac4, scone, museum, stair01-04 each expose a single 'zone' sensor, so active_sensors is 0/1 there (tokyo and homes have many).
- D012 Site roles (from site_summary.csv, not assumed): ac2 dropped (4.5 KB file). Primary office clients: ac1, ac3, ac4, scone, tokyo (5, not 6 as the plan assumed because ac2 is unusable) + museum (6th client; only 2 test days after 7-day gaps, so mainly a training client). stair01–04 = extra clients for the many-clients ablation (stairwells are not workplaces; presence there is transit). Total 10 office-type sites meet >=180 usable days. Homes: aruba (individual regime, 1 resident), tulum1/tulum2/milan/cairo aggregate.
- D013 Many offices pre-date the 2016+ weather window (ac4 2011–13, scone 2013–15, ac3 from 2014, tokyo from 2007): same replay-by-(day-of-week, season) rule as D007 applies. tokyo spans 17 years; the simulator will use its most recent 3 years only (documented in sim config).
- NOTE presence is high at several office sites (mean 0.33–0.69 over 24 h; first arrival often early morning) => PIR sites are noisy / 24h-used spaces; limitation for the 'occupancy' claim.
- D014 Calibration: with the initial a-priori parameters (sim.yaml, untuned) B0/B1 annual electricity on all 10 sites x 2 methods fell inside BDG2's 10th-90th percentile (53-293 kWh/m2/yr) => NO parameters were changed. Honest reading: this is a plausibility check only, not validation; the total is dominated by plug loads (35-67 kWh/m2) and BDG2 offices are mostly non-tropical. Weather year used: Surat 2019 (replayed occupancy, D007).
- D015 At 24h-active sites (ac1, stair01) B1 uses MORE energy than B0 (presence is almost always on, so the PIR rule rarely sets back); gains of occupancy-aware control are limited where the PIR signal is noisy/always on. Report as finding.
